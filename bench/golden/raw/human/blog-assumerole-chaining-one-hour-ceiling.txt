A nightly job ran for three weeks, then stopped at 01:00:03 with  . The error named a token — not a bucket, not a policy. Nothing had been deployed; the only change was the size of the dataset, from fifty minutes of work to seventy.

The credentials had an expiry printed on them, and nobody had read it.

The short version

Software does not log into S3 with a password. It gets a short-lived pass — an access key, a secret, and a session token — with an expiry written inside. Every request carries it.
A role can use its own pass to fetch another role's pass. That second pass is capped at 3600 seconds by AWS STS, whatever the maximum session duration of either role says. It is the one place in IAM where a role's own setting stops applying.
Ask for longer and the call fails immediately with a  . Ask for nothing and you get 3600 seconds without warning — which is how a forty-minute staging run turns into a four-hour production job that dies at the hour mark.
The failure is not retryable: S3 answers  , and every part already uploaded to an unfinished multipart upload keeps billing at $0.023/GB-month until something aborts it.

What actually happens

When a program needs S3 access it calls   and receives three strings plus an   timestamp. The three strings are handed to the SDK; the timestamp is usually thrown away. That timestamp is the whole subject of this article.

The hop is what breaks it. A user with a long-term access key assumes   — the initial assumption, where  's own maximum applies. Then  's session token assumes  . That is role chaining, and AWS states the rule plainly: chaining limits the role session to a maximum of one hour, regardless of the maximum session duration configured for individual roles. Ask for more on that second call and the operation fails.

 

Two consequences follow, and only one is loud. The loud one: you request twelve hours on a chained call, it fails at the moment it is made, and the job never starts — annoying, easy to find.

The quiet one: you request nothing.   is optional, so   returns 3600 seconds, the job starts, and it runs until minute 60. Nothing in the response, the ARN or the logs says "this is a chained session" — the ARN has the same shape at any depth,  . The only observable difference is the   value, and comparing it with the work is the only way to know.

Three properties matter when planning around it. A chained session cannot call   or  , so an MFA session must be minted before the first hop. Session tags survive only when declared transitive. And compute-held credentials on EC2, ECS, EKS and Lambda are not subject to the role's maximum session duration — the platform refreshes them, which is why the same code works in a container and fails on a laptop.

Doing it right

1. Read the expiry you were given, not the one you requested.

 

Two timestamps an hour apart against a four-hour job is the bug, found before it happens. Run this from the profile the job actually uses, not from your admin profile.

2. Make the job refuse to start when the session is too short.

 

A job that exits in two seconds with a clear reason is a monitoring event. A job that exits after sixty minutes is an incident.

3. Remove the hop where the permissions allow it. One role carrying the union of what the two did is simpler, and keeps a twelve-hour maximum available. Where the split exists for a reason, federate straight into the target role — OIDC or SAML issues the session directly, so the first assumption is also the last.

4. If the hop stays, cut the work into sub-hour chunks. Checkpoint by key prefix or object list, re-assume per chunk, and make each chunk idempotent so a re-run overwrites rather than duplicates. Or move the long leg onto compute whose credentials the platform refreshes — an instance profile, a task role, a pod identity.

5. Abort the leftovers, so a failed run stops costing money.

 

One day is aggressive on purpose: an upload that legitimately spans a day is a design that will break at the hour mark anyway.

6. Alarm on the code, not on the status class. Count   separately from the rest of the 4xx responses. A single occurrence means a job is already dead, and the count will tell you how many of them died at the same minute — which is what a shared credential looks like.
