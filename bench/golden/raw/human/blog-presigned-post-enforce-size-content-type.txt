Every "upload directly to S3" feature starts the same way: the server hands the browser a presigned URL, the browser PUTs the file, the object appears. It ships in ten minutes, and quietly grants anyone holding that link the right to store four gigabytes of anything in your bucket. The fix is a different primitive: a presigned POST, where the permission is a document stating the size and type it will accept, signed before a single byte moves.

The short version

A presigned URL signs one request — a host, a path, a verb. It never says how many bytes may follow.
A presigned POST signs a policy: a short JSON document listing conditions the upload must satisfy, such as a byte range and a content-type prefix.
S3 checks the policy first, then counts the body as it arrives. An oversized file stops at   and nothing is stored.
The limit lives in the signature, so it holds even if the browser is modified or replaced by  .
The hours are in the audit, not the fix. The policy is ten lines; finding the stray objects that got past the old endpoint means listing the bucket and sorting by size.

What actually happens

A presigned PUT is an HMAC over a canonical request: method, host, path, and the headers you chose to sign. The body is not part of it. The signature says "PUT to this key is allowed until this time", and the client decides what to send. You can sign   so a different type fails with  , which is a type check and not a size check — the length is still whatever the client announces.

A presigned POST moves the constraints inside the signature. You write a policy document, base64-encode it, and HMAC-SHA256 the base64 with the signing key derived from your secret, the date, the region and  . That signature goes back to the client as a form field, with the encoded policy beside it. The browser then builds a   body: the auth fields, whatever metadata you allowed, and the file.

The limit is enforced while streaming. S3 counts the file part as the body arrives, stops reading the moment the counter passes  , and stores nothing partial — a documented property of the operation, not something to hope for.

The form has a size of its own. Form data and boundaries, excluding the file contents, cannot exceed 20 KB. A normal policy is under 1 KB, so you only meet this by stuffing base64 thumbnails into  ; that metadata belongs in your database.

The file must be the last field. AWS says it twice: "make sure that the file field is the last field in the form". Put   after it and the key arrives missing.

No size cap on a PUT. There is no   equivalent in a PUT signature; the nearest thing is signing a   header, which browsers do not let JavaScript set. That gap is what keeps the insecure pattern alive.

Provider deviation is real, and one is fatal. A delete is not a refund. With versioning on, removing an oversized object leaves a noncurrent version, which stays billable.

The browser hides the reason. When S3 stops reading a body the client is still writing, the socket drops mid-send and   often reports a network error instead of the  .
