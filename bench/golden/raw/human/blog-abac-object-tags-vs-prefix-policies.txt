The short version

A prefix is part of the file name:  . A tag is a label stuck to the file itself:  .
AWS can check a tag only when someone asks for one specific file. When a program lists a folder, the tags are not returned at all — so a tag-only design hands people a file list full of things they cannot open.
Storing tags is cheap: $0.0065 per 10,000 tags per month on AWS (list price, us-east-1, 3 November 2026). Three tags on a million files is about $2 a month. Labelling the files you already have, and reading those labels back, is where the money and the hours go.
A bucket policy cannot exceed 20 KB. One realistic tenant statement is about 330 bytes, so roughly 60 tenants fit before someone starts splitting buckets.
Tags cannot stop a delete. AWS explicitly does not support the tag condition on PUT or DELETE requests. Deletion control has to come from a prefix or from Object Lock.
Verdict: prefixes for navigation, tags for authorisation on reads. Not one or the other.

What actually happens

S3 has no folders. A key is one string —   — and the slashes are a convention that the API calls a prefix when you pass it as a filter. A policy matches keys with wildcards on the ARN, so   is a prefix rule whether or not anyone calls it that.

The consequence is structural: a prefix gives you exactly one dimension. AWS says so in its own object tagging documentation — prefix-based categorisation "is one-dimensional". Everything under   is one category, and the only way to express a second distinction is to encode it into the key itself, where it becomes permanent:  . Renaming later means copying every object.

Tags add the missing dimension. Each object carries up to 10 tags, keys up to 128 Unicode characters, values up to 256, and both are case-sensitive. They live beside the object, not in its name, so they can be changed without rewriting anything.

That asymmetry is not a bug to work around. It is the shape of the system: prefix answers "what is here", tag answers "may I have this one".

Where it bites

1. Anyone who can tag can grant themselves access. A role with   and   on   can upload a file, tag it  , and read it back — or re-tag an existing file it owns and read that. The tag condition is a trust boundary only if tag-writing is restricted. AWS provides   precisely for this: every write must carry an approved tag set, so   cannot be arbitrary.

2. The delete gap is real and surprising. The AWS documentation is explicit that   is not supported for   and  : "you cannot create a policy to grant or deny a user permissions to delete or overwrite an object based on its existing tags." A policy written as "tenants may delete only their own objects, by tag" does not do that. It does nothing on the delete path, and   returns   while the data goes. Deletion control is prefix-based, or it is Object Lock, or it does not exist.

3. Prefix policies die at the 20 KB wall. A bucket policy is limited to 20 KB. A single realistic tenant statement — Sid, Principal, two actions, one resource ARN, two tag conditions — measures 333 bytes when minified. That is about 61 statements before the policy will not save, and you still need the bucket-level statements for listing, uploads and the admin role. The symptom is not an error at design time; it is a   or a silent truncation during a Terraform apply, on the day the sixty-second customer signs.

The usual reaction is one bucket per tenant. That works, costs you cross-bucket reporting and a bucket quota per account, and multiplies every automation by N.

4. Tags do not travel everywhere.   defaults to  , so an ordinary copy keeps the tag set — good. But S3 directory buckets (Express One Zone) support only an empty tag set and return   when a copy would bring non-empty tags across. And Cloudflare R2 implements no tagging at all:  ,   and   are listed as unimplemented in the R2 S3 compatibility matrix, and   is rejected on  . An access model built on   is an AWS general-purpose-bucket model, and migrating to R2 later means rewriting the authorisation layer and re-keying the namespace.

5. An untagged object becomes invisible, not just unreadable. Every write path must tag: the SDK upload, the Lambda, the Airflow task, the CSV someone dropped in with  . Miss one and those objects fail every tag condition, which after a policy cleanup reads as "the file disappeared". Worse,   on a denied object returns   — identical to the message for a key that does not exist, and one of the several ways the five-gate evaluation order can refuse a request while reporting nothing useful — so the first hour of the incident is usually spent proving the file is still there:

 

6. Enumerating tags is a request-per-object job. Filtering a listing client-side means one   call per key. On a million objects that is a million GET requests — $0.40 in request charges at $0.0004 per 1,000, which is trivial, and roughly 5.5 hours of wall clock at 50 requests per second, which is not. Worked example: your own latency per call sets the real number, and S3 does not batch tag reads.

Doing it right

Step 1 — split the two jobs on paper. Write one sentence and keep it: prefixes name the namespace a principal may list; tags carry the attributes that decide what it may read. Any key that encodes a security attribute is a key you can never rename.

How S3 Explorer fits

Tag-based authorisation produces exactly the confusion this article describes: a key that is listed and then refuses to open. S3 Explorer lets you look at both halves of that from one window — the folder navigation shows the prefix tree a principal actually sees, and the object's Metadata tab shows what the bucket stores for that key, so you can tell a mis-tagged object from a mis-scoped policy before you edit anything. The connection test on the connection form reports how many buckets the credentials can see before you save the profile, which is the fastest way to check that a support role has the namespace you think it has.
