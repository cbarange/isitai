A nightly backup starts answering  , and the message is about Content-MD5. No MD5 was ever sent: the SDK sends a base64 CRC now. Nothing in the repository changed between the last good run and the first bad one — a default did, and it decides which checksum travels with the object.

The short version

Since 1 December 2024 S3 stores a CRC-based checksum on every new object, even when the client sends none; the algorithm it picks for itself is CRC64NVME.
The algorithm the client sends is a separate decision, and the clients disagree: AWS CLI v2 defaults to CRC64NVME, while boto3, Go, Java and JavaScript default to CRC32. One bucket can hold both without anyone choosing.
Reading the value back is opt-in: without   a   returns no checksum at all, on an object that has one.
A mismatch is  , whose documented text talks about Content-MD5 whatever you sent, and the SDK re-sends the whole request first — six attempts by default on one small object.
The cost is CPU, not storage. A pure-Python CRC64NVME runs at 3.8 MiB/s on this machine against 5.86 GiB/s for the C library: 7.5 hours instead of 18 seconds for 100 GB.

What actually happens

The checksum is computed by the client, before the first byte moves. It travels as a header named after the algorithm —  ,   — with the 8-byte or 4-byte value base64-encoded, which is why a CRC64 looks like a twelve-character string such as  . As an   header on a signed request it joins  , so a middlebox that rewrites it breaks the signature, not the checksum.

On arrival S3 recomputes the value over the bytes it received and compares. Equal: the object is stored and the checksum goes into its metadata, re-readable months later. Not equal: nothing is stored.

Since 1 December 2024 that happens whether or not your code participates: the AWS announcement says S3 computes a CRC and stores it for new objects even when the client sends nothing, and the user guide adds that when neither you nor the SDK chooses an algorithm, S3 uses CRC64NVME. That page lists ten accepted algorithms, five added on 23 April 2026.

 

Whether the stored value can verify a file depends on the checksum type. For a multipart upload it is either   — the checksum of the concatenated part checksums, exactly like a multipart ETag — or  , computed as if the object were one stream. Only the CRC family can linearise, so only CRC32, CRC32C and CRC64NVME support  , and a composite value cannot be compared with a CRC computed over the whole file.

Checklist

[ ] Every upload path names its checksum algorithm, or documents the SDK default it relies on.
[ ] The checksum is computed before the upload and compared with the value the server returns.
[ ] Multipart paths that need whole-file verification declare  , and never compare a composite value to a local CRC.
[ ] Downloads enable checksum mode, or the SDK validates the response.
[ ] The reader accepts whichever algorithm the object carries, and a missing checksum fails the job.
