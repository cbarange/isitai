A cleanup script lists a bucket, deletes what it finds, prints  , and leaves 97% of the objects in place. Nothing errored. The script asked for the bucket contents once, received a page of 1,000 entries, and treated that page as the bucket. Every S3-compatible endpoint behaves this way, and the response says so — in  , a field most code never reads.

The short version

One list request returns at most 1,000 entries. A bucket holding ten million objects takes ten thousand requests to walk.
A folder in the response is one of those 1,000 entries. A page can come back with 10 folders and 990 files, and still be full.
The end of a listing is signalled by  . A page shorter than   is not the end.
Asking for   returns 1,000 entries on a real endpoint and 2,501 on the mock server most tests use — so a passing test proves nothing about production.
Ten million objects is 10,000 billed requests to enumerate: $0.045 on Cloudflare R2 at $4.50 per million Class A operations. The script that misses objects costs more than the listing.

What actually happens

  answers with a page. The API reference opens with "Returns some or all (up to 1,000) of the objects in a bucket with each request", and the   parameter repeats it: "By default, the action returns up to 1,000 key names. The response might contain fewer keys but will never contain more."

So 1,000 is not a default you can raise. It is the width of the pipe. Two fields describe what came back:  , the objects, and  , the number of entries the page actually carried. A third,  , says whether another page exists, and   — "obfuscated and is not a real key" — carries the position forward.

The ceiling costs nothing per object: AWS's own guidance says list performance "is not substantially affected by the total number of keys in your bucket". A million keys and a thousand keys answer in the same time. What changes is how many round trips you need, and each one is billed.

 

Now the part that breaks code. Add   and the response rolls up everything under a common prefix into a single   entry, the thing a GUI draws as a folder. The API reference is explicit that the rollup is not free: "Each rolled-up result counts as only one return against the MaxKeys value." A page is therefore up to 1,000 entries, not 1,000 objects, and the mix is whatever the key order produces.

Browsing is not free either. AWS bills LIST requests in the same class as PUT, and the pricing page states that browsing the console "incur[s] charges for GET, LIST, and other requests that are made to facilitate browsing". A person clicking through folders generates exactly the calls a script does — the S3 Explorer walkthrough shows that browse call by call — and the invoice consequence is set out in the request charges that make up most of an S3 bill.

Doing it right

1. Loop on   and nothing else. The SDK paginator does it for you; hand-rolled loops should copy its shape exactly.

 

2. Count entries with  , never with  . The difference between the two is exactly the number of folders on that page.

3. Use   when the job must be restartable. AWS documents it as "where you want Amazon S3 to start listing from" and accepts "any key in the bucket", so a crashed job can resume from a key you persisted, without storing an opaque token that may not survive a client upgrade.

 

4. Set   below the ceiling when you need predictable pages. A page size of 500 makes retries cheaper and keeps a single slow response from stalling the whole walk. Above 1,000 is silently clamped on real endpoints.

5. Prove the cap on the endpoint you deploy against, not on the mock. One run of the probe above answers what no test double can: whether this provider honours  , whether prefixes share the budget, and what its token looks like.

6. Verify a deletion or backup job against an independent count. Log the entries processed and compare with the number the provider reports elsewhere: a job that lists 1,000 entries from a 30,000-object bucket and logs   is indistinguishable from success in every log you have.
